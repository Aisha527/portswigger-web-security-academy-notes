# 0.CL Request Smuggling — PortSwigger Lab

## Overview


**HTTP Request Smuggling** occurs when the front-end and back-end servers interpret the boundaries of an HTTP 

request differently, causing **desynchronization (desync)**.


In a **0.CL attack**, the back-end effectively processes the request as having a zero-length body, despite the 

front-end processing a `Content-Length` header. This can allow attacker-controlled data to be interpreted as a 

separate request.


The advanced 0.CL technique can use an **early-response gadget** and **double desynchronization** to make a 

smuggled request affect a subsequent victim request.


---


## Lab Objective


The goal was to exploit the desynchronization so that the following XSS payload:


```html

<script>alert()</script>

```


would be delivered through the victim's request and execute in Carlos's browser.


---


## Initial Request


I initially tested the target with:



```http

GET /resources?asdf<asdf HTTP/2

Host: LAB-ID.web-security-academy.net

Cache-Control: max-age=0

```


The final exploitation, however, was performed using **HTTP/1.1 and Turbo Intruder**.


---


# Exploit Structure


The attack follows this sequence:


```text

Early Response

      ↓

   CL.0 payload

      ↓

 Smuggled request

      ↓

 Victim request

      ↓

    alert()

      ↓

   SOLVED

```


The important concept is that the attacker is not directly sending the XSS to Carlos. Instead, the attacker 

manipulates the connection state so that the **smuggled request is interpreted in the context of a subsequent 

victim request**.

# Script Breakdown


### 1. Request Engine


```python

engine = RequestEngine(...)

```


Configures Turbo Intruder's request engine.


Important settings:


* `concurrentConnections=10` → uses multiple concurrent connections.

* `requestsPerConnection=1` → controls requests per connection.

* `maxRetriesPerRequest=0` → disables automatic retries.

* `timeout=5` → five-second timeout.

---


### 2. Host


```python

host = 'LAB-ID.web-security-academy.net'

```


Stores the lab host so it can be reused throughout the payload.



If the lab is restarted, the `LAB-ID` may change.



---


### 3. Offset


```python

Offset = 9

```


Used to calculate the `Content-Length` for the early-response request:


```python

cl_value = str(len(chopped) + Offset)

```


The value is specific to the request alignment used in this exploit.


---


### 4. Early Response Gadget


```python

earlyresponse = (...)

```


The `/resources/images/blog.svg` endpoint is used as an **early-response gadget**.


The important part is:


```http

Content-Length : %s

Connection: keep-alive

```


The `%s` placeholder is replaced with the calculated `cl_value`.


The purpose of the early response is to help create the required desynchronization without waiting indefinitely 

for the expected request body.


---


### 5. Chopped Request


```python

chopped = (...)

```


This request helps establish the correct **request-boundary alignment**.


Its:


```http

Content-Length: 123

```


is part of the CL.0 payload construction.


The key idea is that the front-end and back-end do not necessarily interpret the resulting byte stream in the same 

way.


---


### 6. Revealed Request


```python

revealed = (...)

```


This request is placed after `chopped` and before the smuggled request.



It helps position the request stream correctly during the desynchronization process.

---


### 7. Smuggled Request


```python

smuggled = (...)

```


This is the malicious request.


The important part is:


```http

User-Agent: XXX"><script>alert()</script>"XXX

```


The XSS payload is embedded in the `User-Agent` header.



The request is intended to become the request interpreted by the back-end/victim context after the connection has 

been desynchronized.

---


### 8. Victim Request


```python

victim = (...)

```


Represents Carlos's request to:


```http

GET /

```


This request is important because the exploit needs a **subsequent request on the affected connection**.


The smuggled request is not useful by itself; the goal is to manipulate the connection so that the victim request 
is processed in the attacker-controlled state.



---


### 9. Repeating the Attack


```python

while True:

```


The sequence is continuously repeated because request smuggling is sensitive to connection state and timing.


Each iteration sends:


```text

Early Response

       ↓

     CL.0

       ↓

    Victim
```

---


### 10. Calculating Content-Length


```python

cl_value = str(len(chopped) + Offset)

```


Calculates the required `Content-Length` dynamically based on:


```text

length of chopped + Offset

```


This value is then inserted into the early-response request.


---


### 11. Queueing the Requests


```python

engine.queue(earlyresponse, cl_value, label='Early Response')

```


Queues the early-response request.


Then:


```python

engine.queue(

    chopped + revealed + smuggled,

    label='CL.0'

)
```


concatenates the three components:


```text

chopped + revealed + smuggled

```


and sends them as the CL.0 payload.


Finally:


```python

engine.queue(victim, label='Victim')

```


sends the simulated victim request.

# Key Takeaways


* **0.CL** is a request-smuggling/desynchronization technique.

* The exploit relies on different request-boundary interpretations between HTTP components.

* An **early-response gadget** helps establish the required desync.

* `chopped` and `revealed` help achieve the required request alignment.

* `smuggled` contains the malicious XSS request.

* `victim` represents the subsequent victim request.

* The attack is repeated because the correct connection state may not occur on every attempt.

* `### SOLVED ###` is the actual success condition, not simply `Fails: 0`.
